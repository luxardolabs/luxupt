## Fixes

- **Timelapse jobs could vanish mid-flight.** `JobProcessor.start_job` discarded its `asyncio.create_task` result, so the event loop held only a weak reference and an in-flight job could be garbage-collected with no error and no log (ruff RUF006).
- **Two camera links returned nothing.** The camera panel's "View Images" and "Timelapses" sent `safe_name` into a `camera_id` (UUID) column — zero rows every time, while the filter dropdowns on the same pages already sent the UUID.
- **The "timelapse already exists" check never fired** — it compared a safe name against the UUID column, so it could re-encode work that already existed.
- **13 timelapse rows were invisible to the UI** — a retired code path wrote `camera_id=""`. Repaired by migration `9f3d0d41053d`.
- **GET page renders wrote to the database.** The settings CRUDs were lazy get-or-create and the users page synced the env user on every render, so 13 GET routes reached a write — CSRF-reachable under `SameSite=Lax` (`fw.state_changing_get`, now 0).
- **The About page rendered blank values** — it read three `config` keys the view never provided; exposed by turning on `StrictUndefined`.
- **A flaky test was a real test bug.** `test_tampered_token_rejected` rewrote the LAST base64 character of a JWT signature; that character carries only 4 significant bits, so for 3 of 64 values the tamper decoded to the same bytes and the token stayed valid (~4.7% of runs).
- Blocking `pathlib`/`os.path` calls moved off the event loop (ruff ASYNC240), and four more that ASYNC240 could not see. The worst: `ProtectClient._stream_to_file` opened the output file synchronously and did a blocking `f.write(chunk)` inside `async for resp.aiter_bytes(...)` — so a video export (tens of MB at ~45 MB/s) stalled the worker on a synchronous write for every chunk of the download, which is precisely what streaming it was meant to avoid.
- **Five swallowed exceptions.** Each was legitimate best-effort cleanup, but discarded the error, so a failure was indistinguishable from success. They now narrow the type they expect and log anything else; the two `contextlib.suppress(Exception)` sites became real `try/except`, since `suppress` cannot log.
- **Today/Yesterday could read "Tomorrow".** `day_label` took `.date()` off a UTC instant, so a 9pm local capture labelled as the next day.
- **A duplicate dict key silently dropped a value** — `available_date_options` was written twice in the same literal (ruff F601).

## Refactors

- **Two session owners.** Added `get_db_context` (the non-request owner) and routed all 46 raw `async_session()` mints through `get_db` / `get_db_context`. A raw factory session in a background path never commits and takes a second pooled connection.
- **The view seam owns its web outcome** — `fw.no_passthrough_view_service` to 0; routers thinned to "receive request → call one service method → return the response".
- **Templates render, they do not compute** — `fw.no_template_logic` to 0. Duplicated camera/date option shaping moved into the view layer; URL assembly moved out of templates (and now escapes via `urlencode`).
- **UI composes macros** — `fw.no_hand_rolled_components_in_pages` 75 → 15; library gained `toggle_row`, `radio_card` (card/list/tile), and `text_input(suffix=, align=)`.
- **One name per threaded value** — `fw.no_threaded_aliasing` to 0; CRUD parameters renamed to the columns they filter.
- Display formatting moved to the edge (`fw.strftime_is_display_only` to 0); recording-range bounds now render in the viewer's timezone rather than the server's.

## Time

- **Timestamps are tz-aware UTC everywhere** (`luxarch --playbook datetime-utc`). Previously every timestamp was built with `datetime.now()` — naive *and* local, an offset-less wall-clock that only meant something on the machine that wrote it.
- The five arch datetime rules were **already green** before this, because every column was `DateTime(timezone=True)`. That is the trap the playbook names: an aware column is not a safety net. Measured on this stack — write `datetime.now(UTC)` to such a column on `sqlite+aiosqlite`, read back `tzinfo=None`. SQLite has no `timestamptz` and SQLAlchemy's SQLite `DATETIME` storage format carries no offset field, so the offset is dropped on write.
- That is why this was not a `now()` → `now(UTC)` sweep. Half-converted it is **worse** than untouched: uniformly-naive comparisons work, but a naive DB read compared against an aware `now(UTC)` is a `TypeError`. `app/db/types.py::UtcDateTime` closes it — UTC on bind, UTC re-attached on read, and a **naive bind is rejected** rather than coerced, because a naive value there is a missed construction site and storing a local wall-clock as UTC is the corruption the type exists to stop.
- **The business zone is a decision, not formatting** (`DISPLAY_TIMEZONE`, `app/utils/timezones.py`). The image and video archives are foldered by local date, so computing the day in UTC would file every capture after ~6pm US-Central under tomorrow *and* make the archive already on disk unreachable. Every site was classified: `datetime.now(UTC)` where a value is an instant, `business_day()` where a date **names** something (a folder, a title, "today's captures", a Today/Yesterday label).
- **The scheduler stays local on purpose.** A configured "run at 02:00", and a historical daily window of "capture 08:00–18:00", are recurring wall clocks, not UTC instants — the one genuinely-local datum in the playbook. The daily window previously resolved against `start_at.tzinfo` and would have silently become UTC the moment job timestamps went aware.

## Schema / Migrations

- `a2d380f58938` — **baseline schema (additive, structural).** The chain had six revisions and zero `create_table`: `alembic upgrade head` on an empty database died on revision 001. The schema was only ever built by `create_all`, so migrations had never been exercised from empty and no fresh provisioning path worked. Baseline added and the chain re-rooted. `alembic heads` is still `006`, so existing deployments are already at head and unaffected.

- `9f3d0d41053d` — **data backfill (non-destructive).** Fills `camera_id` on timelapse rows written with `""`, only where the safe name resolves to exactly one camera. Downgrade is a no-op.

- `c4e7b1a90f22` — **timestamp conversion (data, reversible).** Without it every stored row is wrong under the new read path: a value meaning "14:00 Chicago" would start reading as "14:00 UTC" — same wall-clock, different instant, displayed five or six hours late. Converts the **14 application-written** columns.

  `created_at`/`updated_at` on the `TimestampMixin` tables are deliberately **excluded**: they carry `server_default=func.now()`, and SQLite's `CURRENT_TIMESTAMP` is **already UTC**, so shifting them would break them. `jobs.created_at` is *not* one of those — `jobs` does not use the mixin — so it **is** shifted. The distinction is spelled out in the migration rather than inferred from the column name, because getting it wrong in either direction moves data silently.

  Converted per-row in Python rather than as a SQL `'+N hours'`, because the offset is not constant. Verified against a copy of the bb database (423k rows) at `TZ=America/Chicago`: CST winter `12:00 → 18:00` (+6h), CDT summer `12:00 → 17:00` (+5h), the ambiguous repeated hour `01:30 → 06:30` (+5h, first occurrence), `cameras.created_at` untouched. A flat `+6` would have been an hour wrong on every summer row — most of the year. The downgrade restores the originals byte-for-byte, round-tripped on the same copy.

  **Deploying:** run the upgrade with `TZ` (or `DISPLAY_TIMEZONE`) set to the zone the data was written in. The migration refuses to guess an unknown zone, and is a no-op if that zone is already UTC.

- `MetaData` now carries the canonical fleet `naming_convention`.
